### 2. 機構化した対策自体が副作用を持った

追加した workflow（#1770）には、次の concurrency 設定があります。

```yaml
concurrency:
  group: blocked-label-guard-${{ github.event.pull_request.number }}
  cancel-in-progress: true
```

PR #1776 で同一 head SHA に対して 2 つの run が同時に発火し、片方が cancel されました。`Blocked label guard` は必須ステータスチェックであるため、`cancelled` の check-run が残った結果として `mergeable_state` は `blocked` のままになります。他の必須チェック 6 件はすべて pass しており、`behind_by` も 0 でした。原因が「ラベルが付いている」ではなく「run が cancel された」ことなので、エラーメッセージからは理由を読み取れません。自動では解消せず、`gh run rerun` による手動介入を要しました（#1778 で追跡）。

### 5. 件数の実測が worktree の重複計上で 3 者とも誤った

「正本」という語の出現件数を測る場面で、レビュアー・実装者・オーガナイザーの 3 者がそれぞれ異なる誤値を報告しました。

| 計測者         | 報告値                  | 手法                       |
| -------------- | ----------------------- | -------------------------- |
| レビュアー     | 81 箇所                 | `grep -rn ... \| wc -l`    |
| 実装者         | 13 箇所                 | `grep -ro ... \| wc -l`    |
| オーガナイザー | 92 箇所 / 37 ファイル   | `grep -ro` / `grep -rl`    |
| **真値**       | **7 箇所 / 5 ファイル** | `git grep -o ... \| wc -l` |

原因は 3 者に共通で、`grep -r` が `.claude/worktrees/` 配下の作業コピーまで走査することでした。本リポジトリでは agent worktree を常用するため、`grep -r` の件数は稼働中の worktree の数だけ増えます。値が再現しないうえ、測定した時点の worktree 構成に依存します。

3 者は独立に測定しており、互いの値が食い違う事実も観測できる状態でした。それでも誰も再現確認を行っていません。誤った数値が測定コマンド付きで公開ドキュメントへ載る直前まで進んでいます。**値の不一致それ自体が再測定の合図**でした。

件数を文書へ書く場面では `git grep` を使います。`git grep` は index と作業ツリーだけを対象とし、他の worktree を走査しません。

### 決定論スライスを検討したが、今回は guard に留めた

improvement-flow の Step 2 は「一部だけ決定論で検証できる場合は、検証できる部分を script + CI に切り出したうえで残余を guard に落とす」と定めています。最もコストの高い学び（リリース済み回帰 2 件）について、次のスライスを検討しました。

- **案**: `src/cli.mjs` を変更した PR で `VALID_CASES` の行数が増えていなければ fail する CI チェック
- **実測**: 7 コミットの `VALID_CASES` / `CASES` は順に 0/78 → 30/80 → 36/83 → 41/85 → 54/87 → 79/102 → 79/102。最後の #1777 だけが両方とも据え置き

```bash

git show "<sha>:${F}" | awk '/^const VALID_CASES = \[/,/^\];/' | grep -c 'argv:'
```

- **不採用の理由**: 案の判定は #1777 で fail する。ところが `src/cli.mjs` の変更には、入力の解釈を変えるものと変えないものがあり、行数の増減はその区別を持たない。誤検出を避けようとすれば、回避のために意味の無い行を足す圧力が生まれ、canary の「表の差分 = 挙動変更の全量」という不変条件（`tests/cli-usage-error-exit-codes.test.mjs:83-84`）を逆に壊す
- **前提**: 「入力の解釈を変えたか」は実挙動の掃引でしか判定できず、決定論のスライスとして切り出せる部分が現時点で見当たらない。判断を要するため guard 側に置く
- **代替の観測点**: 掃引スクリプト（#1761 が 109 形を両実装で機械掃引した手法）を再利用可能な形にできれば、将来この判定は決定論化できる。Carry-over へ記録した

## Dogfooding: improvement-flow 自身

同フローの Dogfooding 節に従い、フロー自体を振り返ります。

- **Step 2 の分類表に gate の観点が無かった**。表は成果物の「形」（guard / command / docs / memory / script）で分類し、対策が止める対象までは問わない。文書として正しく分類された #1752 は、形としては妥当でありながら 5 時間 19 分しか持たなかった
- **Step 1 の一次ソース検証は、値を直したが参照先は直さなかった**。#1731 が追加した測定コマンドの併記に従い、数値をすべて再測定した結果、申し送り値 3 件（PR 26 本 / docs 4 件 / issue 9 件）のずれは公開前に検出できた。一方で canary 件数は、再測定を 2 度重ねてもなお誤ったテーブルを数え続けた（前節 4 を参照）。Step 1 の「一次ソースで裏取りする」は、値の検証としては機能し、参照先の検証としては機能していない
- **Step 1 に測定時刻の要求が無い**。集計期間の終端が未到来のまま集計すると、同じコマンドが後日ちがう値を返す。実際に本振り返りの初稿から 2 時間 45 分で PR は 27 → 30 へ動いた。分子・分母・測定コマンドに加えて、測定時刻の併記が要る
