### L1. 散文のチェックリスト項目は存在し、守られてなお再発した

`docs/development/heuristic-detector-checklist.md` §6 には、#1788 の着手時点で既に次の項目がありました。

> - [ ] 新スキルを heuristic 化する場合は、そのスキルの `applyTo` が対象ファイルに一致することを確認する（`SKILL.md` の `applyTo` を読む）。

この項目は読まれています。#1788 の PR 本文は同ドキュメントの §8 を名指しで引用しました（「`docs/development/heuristic-detector-checklist.md` §8 の要求」）。さらに `applyTo` を根拠にした実効範囲の節を立て、`buildExecutionPlan` を通した実測表まで載せています。それでも実装 `TEMPORARY_SCOPE_EXT_RE` は拡張子しか見ておらず、`scripts/` やリポジトリ直下 config の TODO を指摘として出す状態で、マージ直前の 2 本目のレビューまで進みました。

根本原因は 2 つあります。

**1 つ目は、項目が「読む」としか言っていないこと。** 検出器側にも同じディレクトリ条件を実装せよとは書いていません。読むだけなら達成でき、達成しても実装は一致しません。

**2 つ目は、実効範囲の測定が diff の構成に依存すること。** skill 選択は「diff が applyTo に 1 件でも該当するか」で PR 単位に決まります（`runners/core/review-runner.mjs:79-83`）。一方、選択後の `buildHeuristicComments` は diff 中の全ファイルを検出器へ渡します。1 本目のレビュー対応時、ワーカーは最小 diff（`scripts/a.mjs` 単独）で `skill=not selected` を実測し「`scripts/**` は範囲外」と結論しました。この測定自体は正しいのですが、混在 diff（`src/lib/service.mjs` + `scripts/a.mjs`）では skill が選択され、`scripts/a.mjs` の TODO が発火します。単独 diff の測定から、より広い結論を出していました。

2 本目のレビューは、このリポジトリ自身の `scripts/check-skill-id-references.mjs:49` の follow-up TODO が実経路で発火することを再現して検出しています。

これは**同じクラスの 2 世代目**です。1 世代目は 1 本目のレビューが指摘した「`scripts/build.py` の positive canary が本番経路に到達不能」で、そこでの是正が拡張子の絞り込み（`TEMPORARY_SCOPE_EXT_RE`）でした。どちらも「宣言（applyTo）と実効（検出器）が一致しているか」を、片側の測定だけで判定した誤りです。1 世代目の学びは carry-over メモリに記録されましたが、repo へは codify されていません。improvement-flow の「文書ではなく機構を優先する」（Step 2）がそのまま当てはまります。

本 PR では、この判定を機械検証へ落とします。`tests/heuristic-review.test.mjs` へ canary を 1 件追加しました。`SKILL.md` の `applyTo` を `parseSkillFile` で読み、本番と同じ `minimatch(file, pattern, { dot: true })` で期待値を導出し、検出器の実挙動と突き合わせます。期待値をハードコードしないため、applyTo 側だけを変えても検出器側だけを変えても落ちます。

### L2. `action_required` 未発火は release-please 固有ではなく bot push 全般の現象だった

### L3. `git merge` 後に `npm ci` をやり直さないと stale な dist が clean に見える

PR #1794 の conflict 解消で、`npm ci` → `git merge origin/main` → `npm run build:action` の順に実行しました。`git merge` で `package-lock.json` が更新されたにもかかわらず `node_modules` は旧依存（js-yaml 5.2.2）のままだったため、生成された dist はマージ前の head と完全に一致しました。

問題は、この状態が成功と区別できないことです。`git status --porcelain -- runners/github-action/dist/` は空で、`Action dist freshness` のローカル判定と同じ見え方になります。誤りは `Auto Rebuild Action Dist` bot が正しい dist を push したことで初めて露見しました。

既存のトラブルシューティング表にある「rebuild しても差分が残り続ける」と原因は同じ（`node_modules` が stale）ですが、**症状は逆**です。差分が残るのではなく、出るべき差分が出ません。表に症状として載っていない側だったため、対処が既知であっても引き当てられませんでした。正しい順序は `git merge origin/main` → `npm ci` → `npm run build:action` です。
