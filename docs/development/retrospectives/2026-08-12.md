### O1. 集計値の誤りを 2 回続けて出した

台帳の `reviewAfter` 到来件数を、28 → 0 → 13 と 2 回誤りました。正解は 13 件で、ワーカーの報告値と一致します。3 つの値はいずれも実在の測定結果であり、次のように再現します。

```console
$ git show ea2842ab:docs/development/guard-ledger.yaml > /tmp/gl.yaml
$ grep 'reviewAfter:' /tmp/gl.yaml | awk -v t=2026-08-12 '$2 <= t' | wc -l
      28
$ node -e "const y=require('js-yaml'),f=require('node:fs');
    console.log(y.load(f.readFileSync('docs/development/guard-ledger.yaml','utf8'))
      .guards.filter(g=>g.reviewAfter<='2026-08-12').length)"
0
$ node -e "const y=require('js-yaml'),f=require('node:fs');
    console.log(y.load(f.readFileSync('/tmp/gl.yaml','utf8'))
      .guards.filter(g=>g.reviewAfter<='2026-08-12').length)"
13
```

誤りの型は 2 つあり、別々です。

**1 つ目は、構造化データを素の文字列比較で数えたことです。** 台帳の値は `reviewAfter: '2026-11-10'` と引用符付きで書かれており、`awk` の `$2` には先頭の `'`（0x27）が含まれます。日付の先頭文字（0x32）より小さいため、全 28 件が「到来済み」と判定されました。対処はパーサを通すことです。

**2 つ目は、正しい方法を使いながら測る断面を取り違えたことです。** 2 回目の 0 は、退役判定（#1825）が全件の `reviewAfter` を延長した**後**の台帳を数えた値です。方法は正しく、対象の断面が誤っていました。この型は前回までの規律で塞げません。`git grep` の規律は走査範囲の汚染にしか効かず、`count-in-clean-tree.sh` も同様です。#1828 が挙げた汚染源 3 種にも、断面の取り違えは含まれていません。

**同じ失敗クラスを「4 セッション連続」と自分で指摘した直後に起きています。** 2026-08-04-05 の振り返り 4 節が記録した「参照すべきテーブルが `CASES` ではなく `VALID_CASES` だった」件と、本件の 2 つ目は同型です。どちらも値の再測定は正しく実行され、それでも対象の定義を疑っていません。

対処は improvement-flow Step 1 へ入れました。分子・分母・測定コマンド・測定時刻に加えて、**測定対象の断面（ref・コミット・状態）** の併記を要求します。1 つ目は #1828 が `doc-enumeration-checks.md` の汚染源表へ既に書いており、本 PR では重複させません。

### O2. 設計判断を欠陥と誤診断した

「skill の LLM eval が動いていない」を P1 の欠陥として扱い、「API キー登録が最大のボトルネック」と公開レポートへ書きました。実際にはメンテナの方針であり、LLM eval は CI のオプションであってメインのゲートではありません。意図どおりの構成でした。

測定自体は正しい値を返しています。`skill-eval.yml` の `Run evaluation` と `Check must_include assertions` は、API キーが無いため `steps.check-keys.outputs.has_keys == 'true'` の条件で skip されます。`Skill Evaluation` は必須ステータスチェックにも含まれません。誤りは「測れていない」から「欠陥である」を導いたところにあります。

**「測れていない＝欠陥」と早合点すると、意図された構成を壊す提案が出ます。** 塞ぐべきは「キーが無いこと」ではなく、「その判断と食い違う記述が残っていること」でした。`docs/skills-structure.md` は LLM eval をマージゲートとして記述しており、実態と異なります。#1832 で是正し、決定論的な検証をメインのゲート、LLM eval をオプションとする構造を明記しました。決定論側の実体は必須チェック `Skill schema validation` から走る `npm run skills:validate` です。

同 PR は API キー登録を促す記述を追加していません。方針との整合を保つ側へ倒しています。

### `wc -l` の exit code 潰れを再現した

`scripts/count-in-clean-tree.sh` はコマンドの終了コードをそのまま伝播します。ところがパイプの終端が `wc` の場合、上流が失敗しても `wc` は成功するため、全体は exit 0 で「0 件」を返します。

```console
$ scripts/count-in-clean-tree.sh -- bash -c 'this-command-does-not-exist | wc -l'
bash: this-command-does-not-exist: command not found
       0
# exit code: 0
$ scripts/count-in-clean-tree.sh -- bash -c 'this-command-does-not-exist'
bash: this-command-does-not-exist: command not found
# exit code: 127
```

対処は `bash -c 'set -o pipefail; ...'` を使うことです。script の挙動そのものは変更していません。`bash -c` の中身は利用者が決める領域であり、script 側で強制すると利用者の指定と衝突するためです。
