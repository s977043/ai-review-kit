# ADR-003: 「HITL 既定」から「リスク階層型の人間監督」への移行

## Status

Accepted—安全装置（Epic #1347 S1–S4）を実装してから看板を替える方針。gateDecision 契約（#1349）・監督性/監査（#1350）・gate 執行（#1351: strict_block 消費 + `--gate` CLI + Action `gate:` 入力）がマージ済み。本 ADR は S5（#1352）でその概念変更の理由を記録し、vision / README / pages の文言を追随させる根拠とする。

## Context

River Review は当初、責任境界の原則を「**HITL 既定**（Human-in-the-loop、最終判断は常に人間）」と表現してきた（`docs/vision.md`）。この表現は「すべての変更に人間の承認を必須とする」ことを含意しがちである。

AI 実装エージェント（Claude Code / Codex / Cursor 等）が generate → review → revise のループで多数の変更を継続的に生成する運用では、次の 2 つの失敗モードが同時に現れる。

- **全件人間承認はボトルネックかつ形骸化する**: 変更量がレビュー帯域を超えると、人間の承認は実質的なラバースタンプに退化し、「HITL」は名目だけ残って監督の質はむしろ下がる。
- **無条件の自律継続は危険**: かといってループを人間から切り離すと、リスクの高い変更（境界を跨ぐ設計変更・セキュリティ・不可逆操作）まで自動で通る。

つまり問題は「人間を入れる / 入れない」の二択ではなく、「**どのリスク階層に、どれだけの人間監督を配分するか**」である。人間の注意は希少資源であり、崖に集中させ、原っぱでは節約するのが合理的である。

## Decision

責任境界の原則を「HITL 既定」から「**リスク階層型の人間監督**」へ更新する。変更のリスクを 3 階層に分け、階層ごとに監督の重さを変える。

| 階層                | gateDecision          | 監督モデル                                                                                                                  |
| ------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **崖（cliff）**     | `ESCALATE`            | **HITL 温存** — 人間承認を必須にする。`.river/**` 変更・人間承認要求・リスクマップの `require_human_review`・oscillation 等 |
| **丘（hill）**      | `GO_WITH_OBSERVATION` | **期限付き観測** — 継続を許すが、期限内の観測を課す。期限超過で未レビュー扱いに戻す                                         |
| **原っぱ（field）** | `GO`                  | **自律収束 + 事後監査** — 収束したクリーンな変更は自律継続を許し、run-record / digest で事後に監査する                      |

この変更は「看板倒れ」を避けるため、**安全装置を先に実装してから文言を替える**順序で進めた。

1. **決定論的な gate 契約**（#1349）: `deriveGateDecision` は純関数で、fail-safe（不明・未決は常に GO でなく NO_GO）・崖の無条件エスカレーション（rule 0: `.river/**` は自らを unguard できない）を保証する。
2. **監督性 / 監査**（#1350）: run-record・`river runs digest`・GitHub Actions のジョブサマリ強制表示で、自律継続の実績を人間が事後に検証できる。
3. **執行**（#1351）: deterministic strict_block の無条件 NO_GO 消費、`--gate`（gate.decision → exit code、崖に専用コード 3）、Action `gate:` 入力（advisory → enforced の 2 段階導入）。

## 自己批判（この変更のリスクと反論）

概念の看板を替える以上、都合の良い側面だけでなく危うさも明記する。

- **「人間監督を減らす」ように読まれるリスク**: 本質は「監督を減らす」ではなく「**希少な人間の注意を崖へ再配分する**」である。崖の承認必須は一切緩めない。README / pages でもこの順序（崖の温存を先に述べる）を守る。
- **信頼境界（trust boundary）**: リスクマップ・config・plan テキストは被レビュー変更の著者（=エージェント）の書き込み権限下にある。したがって gate は、エージェントの書き込み権限の外（host / CI checkout）で導出されて初めて信頼できる。rule 0（`.river/**` の変更は無条件 ESCALATE）はこの不変条件の最小限の防御であり、`skills/**` の deterministicGate.command 実行のような広い攻撃面は本 Epic の非スコープ（#1401 で追跡）。
- **fail-safe 方向の徹底**: LLM の出力はエスカレーション方向にのみ効く。不明・未決・malformed は常に GO 側でなく NO_GO / ESCALATE 側へ倒す。この一方向性が崩れると看板は嘘になる。
- **観測（丘）の執行は host 責務**: `GO_WITH_OBSERVATION` の期限は River Review が壁時計で追跡するのではなく、host が執行する。River Review は契約（期限・対象ファイル・期限超過時の扱い）を artifact に載せるだけで、conformance fixture で host 実装を検証する。
- **"HOTL" を宣伝に使わない**: 「Human-on-the-loop」等の自己定義語は、外部から「人間を外した」と誤読されやすい。**見出し・宣伝文言には使わず**、本文の設計原理説明に限定する。看板は「リスク階層型の人間監督」+ 崖・丘・原っぱで統一する。

## Non-Goals

- **auto-merge にはしない**: 自律継続（auto-GO）は「ワークフローの継続」であって「マージ権限」ではない。マージ / required check 化は host / branch protection の責務であり、River Review は Action の出力までを担う。
- **崖の人間承認必須を緩めない**: リスク階層化は原っぱの節約であって、崖の監督を外す変更ではない。
- **既定を advisory から enforced へ勝手に変えない**: `--gate` / `gate: true` は opt-in。デフォルトは advisory を維持し、digest で実績を可視化してからチームが切り替える。

## Consequences

### Positive

- 人間の注意を崖へ集中でき、原っぱでのラバースタンプ化を避けられる。
- gate 契約・監査・執行が揃っているため、看板の各主張（崖=承認必須、丘=観測、原っぱ=事後監査）に実装の裏付けがある。
- 非ループ利用者にも後方互換（advisory 既定、gate は artifact 追加のみ）。

### Negative

- 概念語彙が増える（崖 / 丘 / 原っぱ / gateDecision の 4 値）。用語集と一貫した文言運用が必要。
- 「HITL を弱めた」という誤読リスクが残る。文言順序（崖を先に）とこの ADR による説明で緩和する。
- リスク階層の割り当て（リスクマップ）が誤ると監督配分を誤る。リスクマップの誤りは崖側（ESCALATE / NO_GO）へ倒す fail-safe で緩和するが、正しさの担保はチーム運用に依存する。

## 語彙ルール（Epic #1347 決定事項）

- 看板は「**リスク階層型の人間監督**」+ 崖・丘・原っぱ。
- 「HOTL」は見出し・宣伝文言に使わない。本文の設計原理説明のみ。
- 文言順序は「崖の承認必須（HITL 温存）を先に述べ、その上で丘・原っぱの節約を述べる」。
- Loop 組み込みが本流だが、単体利用も継続サポートする（非ループ利用者への包含メッセージ）。
